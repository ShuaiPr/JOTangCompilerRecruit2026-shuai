# TASK4：合规优化

## 1. 两篇材料里的实际案例

列出的案例本身都是“面向特定样例写优化遍”。

BUAA NEL在 `fft` 样例的 `multiply` 上做“快速乘”，命中后整个函数替换为 `((int64_t)a * (int64_t)b) % mod`， 两个参数、返回 `int32`、递归、四个 `return`（一个返回 `0`，三个取模且模数为常数） 
喵喵队花样滑冰队把 `data = data + func(data, num)` 与 `data = data - func(data, num)` 替换为 `num % 2 == 0 ? data : 0`， 样例 `call`，函数含 3 个基本块、为注释里写死的 IR 特征
同时识别出“只能执行一轮”的子循环并提取出来，把 `O(n²)` 降成 `O(n)`  `large_loop` 样例，11 个基本块、first loop body 的第一条指令是取模、某个基本块恰好 3 条指令 
原末鸣初把 `call` 样例的指令序列 `Sub Call Add Call Sub Br` 逐条精确匹配 ， 同样是样例 `call`，匹配精确到每一条指令 
素履“译”往对冰雹猜想函数用**记忆化搜索**改写；RecursionToLoop：再用**魔数 998244353** 认定 FFT 的 `multiply`，做进一步的快速乘， 前者匹配“含 2 个函数、第一个函数递归、2 个 int 参数、返回 int、无 store 与非递归 call”的 `h-1-xx` 系列；后者直接匹配常数

另外那篇回答补充的现象是：初赛就做模式匹配的队伍把 `large_loop` 做到 1000us（普通实现 300000us），最离谱的把用例跑到 1us；有队伍直接沿用去年冠军的代码连名字都没改（第一行还是 `cmmc`），有队伍被指出后现场删库。结果上，除素履“译”往队因 highlights 发现于申诉之后未受处罚外，其余三支北航队伍各降一档。

## 2. 从案例看违规的判定

这些案例的共同点只有一条：**触发条件来自“这份样例长什么样”，而不是来自语言的语义**。函数有几个基本块、有几条 `return`、`first loop body` 的第一条指令是不是取模、常数是不是 `998244353`，这些都是用例的指纹；命中之后，正确性也不来自被替换的代码本身，而来自赛前已经知道这组样例该算出什么。

由此我理解的边界是：判断一条优化是否合规，不看它写在哪个 pass 里，而看**把条件里的样例属性换成任意一个等价的程序，它还成不成立**。LLVM 的 Loop Idiom Recognition 是通用的等价变换，材料里对标它的 Recursive Function Idiom Recognition 之所以出问题，是因为它匹配的是基本块数量与指令序列这类，为了让“证明”成立还默认开启 fast-math、明确不考虑浮点 overflow；`Instruction List Matcher` 把每条指令都写死，更是把“通用性”直接换成了“对 `call` 这一个样例精确”。

## 3. 合规、违规与投机违规

- **合规**：条件的依据是语义属性（操作码、支配关系、循环不变量、纯度等），对任意合法输入都成立；上面列举的案例都是它的反面。
- **违规**：面向特定样例写优化遍，含写死的替换式、逐条指令的序列匹配、用魔数认定样例；除此之外，材料里“沿用去年冠军代码连名字都没改”和“被发现后删库”属于同一类问题的另一面——前者是抄袭，后者是掩盖。
- **投机违规**：素履队的 O4 没有写死结果，它赌的是冰雹猜想样例的**参数分布规律**；喵喵队甚至给出了看似严格的有理有据的证明，但证明的前提是 fast-math、忽略浮点溢出和“这个形状只会这样出现”。它们都按照评测集里的样子，换一组输入立刻失效。
